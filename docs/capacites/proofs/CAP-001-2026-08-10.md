## 1. Contrat Core audité

Le contrat réel `CAP-CORE-001 / CTR-01` conserve une identité minimale et canonique : référence, type, état, source et historique. Le code Core précise explicitement qu'il ne possède ni profil métier, ni réputation, ni dossier universel ; les produits conservent leurs données d'usage.

Livraison HTTP utilisée par DG Afrique : `GET /identites/{reference}` sous session Core. DG Afrique ne crée pas l'identité canonique dans Supabase.

Fichiers Core audités :

- `zumradeals/gamad-core:core/registre-identites/src/Ctr01.php`
- `zumradeals/gamad-core:apps/console-laravel/app/Http/Controllers/Ctr01Controller.php`

## 2. Session portail DG Afrique

La session portail contient uniquement le support technique nécessaire : token Core, référence d'entité, assurance et expiration. Le cookie est signé côté serveur, HttpOnly, Secure, SameSite=Lax et limité au domaine portail.

CAP-001 extrait désormais la sérialisation/vérification dans `src/lib/gamad-core/portal-session.ts` afin de la tester indépendamment.

Tests ajoutés :

- cookie signé intact et non expiré accepté ;
- payload altéré refusé ;
- signature altérée refusée ;
- session expirée refusée ;
- signature produite avec un autre secret refusée ;
- cookie malformé ou incomplet refusé.

Aucune valeur de test n'est un secret de production.

## 3. Session Core invalide vs panne transitoire

`/api/genesis/account/me` résout l'identité canonique auprès du Core.

Décision CAP-001 explicite :

- Core `401` → `authenticated=false`, HTTP 401, cookie portail effacé ;
- autre panne / indisponibilité → HTTP 503, `authenticated=true`, cookie conservé, erreur `IDENTITE_TEMPORAIREMENT_INDISPONIBLE`.

Cette décision est portée par `src/lib/gamad-core/identity-state.ts` et couverte par tests Node. Le routeur utilise directement cette primitive testée.

## 4. Inventaire des points d'attache métier Supabase

L'audit des migrations ZUMRA montre que les objets métier utilisent la référence canonique Core, sans créer une identité membre Supabase parallèle :

- `zumra_memberships.core_identity_reference` : `NOT NULL UNIQUE` ;
- `zumra_member_profiles.core_identity_reference` : clé primaire, FK vers l'adhésion ;
- `zumra_groups.founder_core_identity_reference` ;
- `zumra_group_members.core_identity_reference` ;
- `zumra_group_roles.core_identity_reference` ;
- événements de groupe : acteur/sujet par référence Core ;
- `zumra_payments.core_identity_reference` : FK vers l'adhésion.

L'API `/api/zumra/me` part de la session portail et requête ces tables avec `session.entity`.

Le client Supabase métier utilise la `service_role` côté serveur avec `persistSession=false`, `autoRefreshToken=false` et `detectSessionInUrl=false` : aucune session utilisateur Supabase n'est fabriquée pour le membre.

Ces constats servent uniquement de preuve structurelle AC-002 ; ils ne valident pas CAP-007, CAP-011, CAP-061 ou un autre CAP métier futur.

## 5. Supabase Auth du back-office

L'ancien back-office CMS possède encore un credential Supabase Auth (`auth.users`) pour les comptes opérateurs `/admin` et la table `profiles` admin/editor.

Décision d'architecture CAP-001 : ce mécanisme est classé **credential du plan de contrôle CMS**, pas identité canonique d'un membre DG Afrique. Il ne doit jamais :

- devenir la clé d'une adhésion ZUMRA, d'un groupe, d'un projet ou d'un satellite ;
- remplacer `session.entity` dans les routes membres ;
- être présenté comme l'identité écosystème de la personne.

Si un futur chantier veut unifier les credentials du back-office avec le Core, il devra le faire explicitement sous le CAP approprié ; CAP-001 constate ici l'absence de concurrence sur le parcours membre.
