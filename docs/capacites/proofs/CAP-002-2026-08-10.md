## Référentiel V0.1

CAP-002 donne à une personne un accès personnel à DG Afrique : création gratuite du compte, connexion, vérification de l'accès et entrée dans Mon espace. Le compte reste distinct de l'adhésion ZUMRA et constitue une porte d'accès, pas une adhésion automatique aux programmes.

Le Core exige EMAIL/TELEPHONE vérifié avant authentification normale. Le code de vérification est livré au canal humain par le Core et n'est pas retourné en clair au navigateur.

## Écarts DG trouvés et corrigés sur la branche

### 1. Renvoi du code

Ancien DG : payload obsolète.

Core actuel :

```json
{"identifiant_reference":"RID-...","destination":"personne@example.com"}
```

Correction : `buildVerificationResendPayload()` et `/api/genesis/account/resend` utilisent le contrat actuel. L'API DG tolère temporairement l'ancien champ `identifier` uniquement pour un onglet ayant chargé un ancien bundle ; la frontière Core reçoit toujours le bon contrat.

### 2. Retour après connexion

Avant : `/connexion?next=...` était ignoré et le succès poussait toujours `/espace`.

Correction : `safeAccountReturnPath()` n'autorise qu'un chemin local DG, refuse `//`, origine externe, schéma externe et boucle `/connexion`. La page `/connexion` et `AccountLogin` réutilisent ensuite cette destination sûre.

### 3. Vérification interrompue

Avant : le dossier `pending` vivait uniquement dans React et disparaissait au reload. Un email non vérifié ne pouvant pas ouvrir de session, l'utilisateur pouvait se retrouver bloqué entre création et connexion.

Correction : dossier local borné `dgafrique_pending_account_verification_v1` contenant uniquement identité Core opaque, RID, référence de vérification, email, échéances. **Aucun mot de passe ni code n'est persisté.** Le dossier peut survivre à l'expiration d'un ancien code afin de demander un renvoi, mais expire lui-même après 7 jours.

### 4. Premier email non livré

Le Core retourne `VERIFICATION_NON_LIVREE` avec les références du compte et du défi déjà créés. DG conserve désormais ces références pour permettre un renvoi sur le même compte au lieu de perdre l'état et de tenter une recréation.

### 5. Limitation de connexion

Core 429 est maintenant traduit en `TROP_DE_TENTATIVES_CONNEXION` côté UI plutôt qu'en indisponibilité générique.

## BLOQUEUR CAP-002 — expiration glissante Core

Le Core `Ctr16` fait glisser `expire_le` de 8 h après chaque vérification réelle valide, jusqu'au plafond absolu de 30 jours. Cependant `AuthentifierApi` utilise ce verdict sans exposer l'échéance actualisée à DG Afrique. DG ne reçoit `expire_le` qu'au `POST /sessions` initial et fixe son cookie navigateur à cette valeur.

Conséquence : le navigateur peut supprimer le cookie DG à l'échéance initiale alors que le Core a prolongé la session. DG ne doit pas inventer localement une nouvelle date.

### Contrat minimal requis

Le Core doit, après vérification authentifiée d'une session, exposer de façon non secrète l'`expire_le` courant attesté — soit via une primitive `GET /sessions/current`, soit via un en-tête de réponse authentifié, soit via un contrat équivalent déjà existant. DG renouvellera son cookie uniquement jusqu'à cette échéance attestée, jamais au-delà.

Aucune nouvelle session, aucun second token et aucune identité parallèle ne doivent être créés pour cette correction.
